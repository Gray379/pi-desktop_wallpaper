# 壁纸 · 背景虚化（local.pi-wallpaper）

给 **PI-Desktop**（第三方桌面端）写的一个壁纸插件：把**你本地的图片**当作整窗壁纸并做背景虚化，
让左侧会话栏、右侧面板、输入栏变成毛玻璃。界面文字始终清晰，只有壁纸本身被虚化。

- 有独立面板（`renderer/index.html`）：**把图片拖进去就换壁纸**，模糊/压暗/适配都是滑块，改完实时生效；
  顶部那条 46px 由面板自己画并标为拖拽区（chrome **v3** paint-through，见下面「设计取舍」）。
- 图片只被**引用路径**，不复制、不上传、不联网；权限三项：`ui.theme`（注册/切换主题）、`ui.panel`（面板窗口）、
  `agent.prompt.inject`（把自己的「避坑技能」交给 Agent 按需加载，见下面「给 Agent 用的技能」）。
- 也保留命令行用法：不想开面板就在「插件设置」里填路径，用命令应用。

> **使用前提（重要）**：本插件**不是独立程序**，必须安装 **PI-Desktop 桌面端**之后，在它的
> 「扩展页 → 加载本地插件」里选本目录（或安装打包好的 `.piplug`）才能使用。
> 它依赖桌面端提供的**运行时主题 API** 与**插件面板机制**：宿主版本需 ≥ `0.15.0`，
> 开发与逐条兼容性核对基于 **0.15.10**；桌面端升级后请先跑「兼容性自检」或 `scripts/compat-check.mjs`。

## 快速开始（面板）

1. **扩展页 → 壁纸 · 背景虚化** → 点行内的「**打开面板**」（或命令面板运行「壁纸：打开面板（拖图即用）」）。
2. 把图片**拖进面板的虚线框**（也可以点它选文件）→ 立刻成为当前壁纸。
3. 用滑块调「背景虚化 / 背景压暗 / 两侧栏遮罩」，下拉调「压暗色 / 适配方式」——都是即时生效。
4. 「移除壁纸」还原桌面端默认底色；「兼容性自检」把宿主环境检查结果直接列在面板里。

> 面板只把**绝对路径**发给插件主进程，自己不做任何文件读写；图片支持
> `png / jpg / jpeg / webp / avif / svg`，单张 ≤ 4 MB（宿主的资源白名单与上限）。
> 拿不到文件路径时（宿主改过取路径 API）面板会提示你改用下面的设置项。

## 备用用法（不开面板）

1. **扩展页 → 壁纸 · 背景虚化 → 插件设置**：把「壁纸图片路径」填成绝对路径，例如 `C:/Users/你/Pictures/bg.jpg`。
   - 资源管理器里 `Shift + 右键` 文件 →「复制文件地址」，粘进来即可（引号与 `file:///` 前缀会被自动清理）。
   - 想多存几张：一行一张，用命令「壁纸：下一张」轮换。
2. `Ctrl/Cmd + P` 运行 **「壁纸：应用本地图片（按设置的路径）」**。
3. 不想要了运行 **「壁纸：移除壁纸」**。

### 设置项

| 设置 | 作用 | 范围 |
| --- | --- | --- |
| 壁纸图片路径 | 绝对路径，一行一张 | `png / jpg / jpeg / webp / avif / svg`，单文件 ≤ 4 MB |
| 当前使用第几张 | 多张时的下标（从 0 开始） | 由「下一张」自动维护 |
| 背景虚化强度 | 只虚化壁纸，文字不变糊 | 0–40 像素，默认 16 |
| 背景压暗 | 壁纸上盖一层半透明色，亮图也能看清白字 | 0–70 %，默认 20 |
| 壁纸提亮 | 给整张图叠一层半透明白，把偏暗的部分（某一边很黑）抬起来 | 0–60 %，默认 0（关闭）；对暗部是加法，和「压暗」方向相反 |
| 两侧栏遮罩 | 左右两栏盖在壁纸上的深浅（用中间栏的底色做遮罩） | 0–100 %，默认 22；**0 = 和中间一样完全透出壁纸** |
| 压暗色 | 纯黑 / 冷灰 / 深蓝 / 暗紫 / 暖棕 / 不压暗 | 默认纯黑 |
| 适配方式 | 铺满裁切 / 完整显示 / 原始大小居中 / 平铺 | 默认铺满 |
| 界面明暗基底 | 壁纸主题用亮色还是暗色配色 | `auto`（默认）/ `dark` / `light`；**照片壁纸请用 auto 或 dark** |

### 命令

| 命令 | 说明 |
| --- | --- |
| 壁纸：打开面板 | 打开拖拽面板（面板里做的一切都走下面同一套逻辑） |
| 壁纸：应用本地图片 | 按当前设置注册并激活壁纸主题 |
| 壁纸：下一张 | 多张图片轮换（写回设置里的下标） |
| 壁纸：移除壁纸 | 删掉运行时主题，并回到桌面端内置的亮/暗主题 |
| 壁纸：兼容性自检 | 报告宿主版本、API 是否齐备、主题是否注册成功、路径是否合法（面板里也能看） |
| 壁纸：恢复正常外观 | 一键把参数回退到推荐值（压暗 20 / 提亮 0 / 遮罩 22 / 基底 auto）并重新应用 |

## 桌面端升级之后，怎么兼容性更新

这套插件的写法就是为这件事准备的：**所有与宿主私有实现耦合的东西只有三处**
——`lib/host-contract.js`（常量、API 清单、面板机制、界面区域选择器、设计 token）、
`lib/theme-css.js`（怎么用它们生成 CSS）、`renderer/index.html`（面板页，只在面板协议变化时才动）。
`main.js` 里没有任何类名或宿主内部名。

升级 PI-Desktop 之后：

```sh
cd pi-wallpaper-plugin
node scripts/compat-check.mjs            # 自动找 E:\PI-Desktop，也可以传安装目录
```

它会把**当前已安装版本**的 `app.asar` 重新解包，逐条核对：

- 宿主版本、插件 API 白名单（`pi.themes.*`、`pi.app.setTheme`、`pi.plugin.setSettings` …）
- 主题 CSS 的限制（≤256 KB，禁 `@import` / `<style` / `<!--` / `javascript:` / `expression(`）
- 本地图片规则（扩展名白名单、单文件 ≤ 4 MB、运行时主题仍接受磁盘绝对路径）
- 主题 id 命名空间 `plugin:<插件 id>:<主题 id>`
- 插件能收到的宿主事件（`plugin:settingsChanged`、`appearance:changed`）
- **面板机制**：面板 bridge 通道、`panel.invoke → onPanelInvoke` 转发、`getDroppedFilePath` 取路径、
  `--pi-plugin-titlebar-height` 拖拽带高度、`pi-plugin-chrome` 协议与 **v3（paint-through）** 是否仍支持、
  宿主是否仍从实时 manifest 读 `ui.panel`
- **壁纸要用到的 12 组界面区域选择器**和 4 个设计 token 是否还在
- 根元素 `#root` 是否还在（壁纸挂在 `html::before` 上，只依赖这块画布）
- 插件自己生成的 CSS 是否仍然满足当前限制

报告里 `[FAIL]` 的就照着改 `lib/host-contract.js` 那一行（比如宿主把 `.work-panel` 改名成别的类名，
就改 `SURFACES` 里对应项的 `selectors`；面板转发机制改名就改 `panelInvocationExport`），改完再跑一次；
`main.js` 不用动。核对全绿之后，把文件顶部的 `verifiedAgainst` 改成新版本号即可。

另外，插件运行时的「壁纸：兼容性自检」命令（或面板里的同名按钮）会报告**实际运行环境**里
API 与主题注册的真实情况——如果某次升级后壁纸不生效，先跑它 + 看插件日志，再跑上面的脚本。

## 目录结构

```
pi-wallpaper-plugin/
├─ manifest.json              # 权限 ui.theme + ui.panel；5 条命令 + 6 个设置项 + 面板声明
├─ main.js                    # 编排：读设置、生成 CSS、注册/应用/自检 + 面板通道回调
├─ renderer/index.html        # 面板页（零依赖，单文件；chrome v2 约定）
├─ lib/
│  ├─ host-contract.js        # ★ 宿主契约：升级后只改这里
│  └─ theme-css.js            # 主题 CSS 生成器（壁纸层、压暗层、毛玻璃区域）
└─ scripts/
   ├─ compat-check.mjs        # 升级后核对宿主契约（解包 app.asar 比对）
   └─ selftest.mjs            # 用桩宿主把 main.js 全流程跑一遍，不需要桌面端
```

## 设计取舍（以及为什么）

- **不依赖宿主自带的壁纸挂点**。0.15.10 的宿主里确实有个 `.app-scenic-backdrop` 元素，但本插件把壁纸挂在
  根元素的 `::before`（`position: fixed; z-index: -1`）上，只依赖 `html / body / #root` 这块画布，
  宿主内部 DOM 结构变化不会让壁纸失效。
- **所有规则都带 `:root[data-plugin-theme="plugin:local.pi-wallpaper:photo"]` 前缀**。宿主选中插件主题时
  会把主题 id 写到 `<html>` 上，并把主题 CSS 追加成 head 里最后一个 `<style>`；这个前缀因此既提高了特异性
  （不会被宿主自己的 `.sidebar-surface { … }`、也不会被以后懒加载的分块样式盖掉），又保证壁纸只在
  壁纸主题生效时出现。
- **只覆盖 `background-color`**，不动宿主其它样式；遮罩色刻意用宿主中间栏的底色 `--ds-bg-primary`
  （**不是**侧栏自己的 `--ds-bg-sidebar` —— 暗色下它等于 `--ds-bg-under` = #000，会黑得很突兀），
  所以左右两栏只会"比中间暗一点"；半透明走 `@supports (color-mix(...))`，老引擎退回实色。
- **顶部那一圈底色全部清掉**：会话标题栏 `.main-titlebar` / `.conversation-topbar`、右上角三个窗口按钮的 120px 条带
  `.window-controls`、以及工作面板那一圈 `.window-chrome-row` / `.work-panel-header` / `.work-browser-chrome` /
  `.file-viewer-header`。宿主给它们写的是不透明的 `--ds-bg-primary`，隔壁的中间栏却是透明的，
  所以只要漏掉一个，那一块就会变成突兀的黑条（"三个符号的位置全黑"就是这样来的）。
  它们和设置页那几块一样带 `!important`，免得被宿主自己的同特异性规则或以后的分块样式盖掉。
- **面板不做任何文件读写**：它只把拖进来的文件解析成绝对路径，交给主进程去注册主题；
  宿主给面板的 bridge 本来就没有自定义 RPC，正路是把未知通道转发给插件自己导出的 `onPanelInvoke`
  （主题工坊也是这条路），所以面板逻辑全部复用 `main.js` 里已经自测过的那套函数。
- **不使用**宿主那套「风景主题卡片 + `--nexus-backdrop-blur`」协议：它要求主题在清单里声明特定变量名，
  且卡片校验与宿主实现绑得很紧；本插件改用运行时主题 API，升级面更小。
- **面板 chrome 用 v3（paint-through）而不是 v2**：v2 会让宿主在顶部铺一条 46px 的「原生拖拽带」，
  那条不属于页面合成范围，在 Windows 上会显示成一条**纯黑**（就是窗口按钮下面那块黑底）；
  v3 下宿主只保留右上角的三个窗口按钮胶囊，顶部由面板自己画成 `.titlebar` 并标 `-webkit-app-region: drag`，
  所以既没有黑带，窗口也照样能拖（市场里的主题工坊用的也是 v3）。
- **不复制你的图片**：宿主只接受绝对路径（`.git`、`.ssh`、凭据等本来就取不到），
  插件因此不需要任何 `fs` 权限；图片被你移动或删除后，应用时会给出中文提示而不是白屏。
- 运行时主题是内存态（宿主如此设计），所以插件在每次启动时重建一次，之前在用壁纸的话会自动重新激活。
  判断"上次在用壁纸"的依据是宿主持久化的主题偏好（`appearance.theme` = `plugin:<插件id>:<主题id>`），
  所以**卸载/重载时绝不把主题改回亮/暗** —— 否则开发热重载、桌面端升级、扩展页开关插件都会静悄悄
  把你的壁纸弄丢（这个坑真实踩过，`scripts/selftest.mjs` 里有一组回归断言盯着它）。
- 唯一强依赖的宿主实现是 `data-plugin-theme` 这个主题钩子：它要是改名了，壁纸会整片消失。
  `scripts/compat-check.mjs` 把它当硬失败报出来，改动点只在一处 —— `lib/theme-css.js` 的 `themeScope()`。

### 顺带说明：不启用壁纸时，两侧栏为什么偏暗

宿主自己的暗色主题里，左栏底色来自 `--ds-bg-sidebar` → `--ds-settings-rail-bg` → `--ds-bg-under`，
而 `--ds-bg-under` 在暗色下就是 **#000**（中间栏是 `--ds-bg-primary` = #181818），所以没启用壁纸时
左栏看起来就是"一块纯黑"。这属于宿主配色，本插件只在**壁纸主题生效时**接管这些面。
想不改壁纸就修掉它，用**主题工坊**（或任何主题插件）改这两个 token 最直接：

- `--ds-bg-under`：从 `#000` 抬到 `#131313`~`#181818` 附近；
- `--ds-settings-rail-bg`：跟着设成同一个值。

改了之后左栏就只比中间暗一点。而一旦启用壁纸，「两侧栏遮罩」这个滑块给的就是同一类控制（0 = 完全一致）。

### 为什么"明暗基底"不能跟着宿主快照走（真实踩过的坑）

宿主在**"用户选的是运行时主题、但该主题此刻还没注册"**的一瞬间（每次启动、每次插件重载都会出现）
会把 `appearance.base` 报成**系统色**。浅色系统上跟着它注册，插件主题的 `base` 就变成 `light`，
界面整片刷白：侧栏遮罩色（用的是 `--ds-bg-primary`）从 #181818 变成 **#fff**，于是左栏像蒙了一层白雾、
背景显示不正常；文字也变成深色，压在照片上根本看不清。

所以主题的明暗基底由**设置项 `base`** 决定：`auto`（默认）只跟随"用户真的选了内置亮/暗"，
其余一律按 `dark` 处理；要亮色请显式选 `light`（只适合很亮的图）。
`scripts/selftest.mjs` 里有一组断言专门盯这个：宿主报浅色时**不允许**注册成亮色。

参数被调花了（或你想一键回到"看得清"的状态），跑命令/面板按钮**「恢复正常外观」**即可。

### 顺带说明：启用壁纸后，某一侧看起来还是"黑"

壁纸生效时，界面能透出的地方只有**压暗**（`dim`，全局往黑压）和**两侧栏遮罩**（`glass`）两层。
如果图片本身某一块就很暗，压暗会把它压到接近 0，看起来就是"一格纯黑"。判断方法很简单：
**把「背景压暗」和「两侧栏遮罩」都拖到 0** —— 这时界面显示的就是图片原样，如果那块还暗，
那就是图片自己暗，而不是界面在压它。这时用**「壁纸提亮」**（0–60 %）把它抬起来，
它对暗部是加法（叠半透明白），所以对"某一边很黑"的图最有效；纯 `brightness` 只会等比放大、救不回黑角。

## 给 Agent 用的技能

本插件带一个技能文件 `skills/pi-desktop-plugin-theming.md`，宿主会把它索引进 Agent 的 `Skill` 工具：
下次遇到"装/更新/排查 PI-Desktop 插件"或"给 PI-Desktop 写改壁纸、主题类插件"这类任务时，
Agent 会自动加载它，而不是重新踩一遍坑。里面是这次做本插件时真实踩过的东西：

- 安装与权限：**改了 `permissions` 必须"卸载 → 加载本地插件 → 同意"**（禁用/启用不会重问）；
  `missing permission: <权限名>` 的含义；数据/注册表/日志/`pi.sqlite`（含 WAL 读取注意）都在哪。
- 主题机制六条：`data-plugin-theme` 作用域前缀、运行时主题是内存态、**别跟随 `appearance.base`**、
  关键 `--ds-*` token 值、**顶部那一圈必须清的面（一个都不能漏）**、面板 chrome 用 v3。
- 不靠肉眼的验证手法：桩宿主自测、解包 `app.asar` 核对、"仿制宿主页 + 同特异性竞品规则"的 Chromium 实测。

维护方式：**直接改这个 markdown 就行**，宿主下次加载（开发目录会热重载）即生效，不需要重新授权 ——
只有增删 `permissions` 才需要重新走一次授权。宿主的上限是 32 个技能 / 单个 128 KiB / 描述 240 字符；
以后内容变多，可以按「安装与权限」「主题改造」拆成两个技能。

> `agent.prompt.inject` 是宿主标记的**高风险权限**（`PluginCheck` 会为此出一行 warning），
> 所以它需要用户显式同意；本插件只用它来交付上面这个纯文本技能，不调用任何注入类 API。
